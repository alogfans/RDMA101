# 5.1 GPU 内存与 GPUDirect RDMA

前面一直从主机内存发送数据。AI 系统中的权重、中间结果和 KV Cache 往往保存在 GPU 显存中，因此还要解决显存怎样进入传输路径的问题。

GPU 有自己的执行和内存管理机制。CPU 能拿到一个 GPU 指针，不表示 CPU 可以像普通数组一样直接访问它，也不表示网卡已经获准使用这段地址。

## 先经主机内存中转

一种容易理解的路径是先把显存数据复制到主机缓冲区，再按之前的方式使用 RDMA。接收端收到主机内存后，再复制到目标显存。这叫 Host Staging。

```text
发送 GPU → 主机缓冲区 → 网卡 → 网络
网络 → 网卡 → 主机缓冲区 → 接收 GPU
```

这条路径增加复制和主机缓冲区占用，但将 GPU 拷贝与网络传输分成了两个可观察步骤。作为首次正确性实验，可以分别验证 GPU→CPU、CPU→CPU 网络传输和 CPU→GPU，再组合起来。

异步拷贝还要求合适的主机内存和 stream 使用方式。每一段开始前都要确保上一段的数据已经就绪，不能因为都是异步接口就按代码调用顺序假定依赖已经建立。

## 网卡直接访问显存

GPUDirect RDMA（下文简称 GDR）允许支持的平台建立网卡与 GPU 显存之间的直接访问路径，省去相应主机中转：

```text
发送 GPU ⇄ 本端网卡 ⇄ 网络 ⇄ 对端网卡 ⇄ 接收 GPU
```

内存仍需要分配、映射和注册，数据也仍经过设备互联。直连是否可用受 GPU、网卡、驱动和拓扑约束；跨根端口或跨 socket 不能一概理解为只是更慢。

对应用而言，成功注册以后仍使用地址、长度和 key 描述操作。差异主要在注册如何取得显存映射，以及传输前后怎样与 GPU 执行协调。

## 显存注册的两类入口

常见 peer-memory 路径由 GPU 与 RDMA 驱动协作，支持时可以对 GPU 指针使用 `ibv_reg_mr`。dma-buf 路径则先导出一个可共享的内存句柄，再通过 `ibv_reg_dmabuf_mr` 等接口注册相应范围。

两条路径有不同的分配、导出和驱动条件，不能混成“任何 GPU 指针都可以直接传给注册函数”。缺少 peer-memory 模块也不能单独证明 dma-buf 路径不可用。

注册时应记录 allocation 类型、注册范围、选中 NIC、导出方式与返回错误。先确认小范围是否支持，再扩大到实际 Tensor。分配器采用 CUDA VMM 时，连续虚拟范围与底层映射的关系尤其需要核对，下一章继续展开。

## 寿命要覆盖两个设备

一块 GPU 内存分配（allocation）可能同时被计算 kernel 和网卡访问。kernel 是提交到 GPU 上执行的计算程序。释放前要确认两类引用都已结束；注销 MR 前也要停止相关远端授权和在途访问。

例如传输库返回一个地址，框架随后从内存池归还了对应 Tensor，地址数字可能仍没变化，但它已经属于另一项计算。网卡继续访问时就可能污染新对象。因此，传输接口需要持有底层分配，而不只是保存指针。

源端生产完成、目标端消费开始的具体时序在 [5.3](03-synchronization.md)讲解。本章先把内存能力与实际路径确认清楚。

## 建立可比较的实验

先使用 CPU 缓冲区验证同一对端路径，再将一端替换为 GPU，最后尝试两端 GPU。每次检查内容、注册结果与实际后端，避免自动 staging 后仍把结果称为直连带宽。

记录驱动、CUDA、rdma-core、allocation 方式和 GPU/NIC 拓扑。本文给出实验组织方法；硬件是否支持某条直连路径，要在所声明环境中实测。
