# 2.5 Completion Queue

请求投递后，CPU 可以继续工作，网卡在后台执行。应用再次需要那块缓冲区时，必须知道操作是否结束。CQ（Completion Queue，完成队列）就是取回结果的地方。

第一篇只有一条 WRITE，所以取到一个成功完成就能继续。加入多个请求后，程序还需要知道是哪一条完成、能归还哪一块内存。这是本章从单请求扩展到并发请求的重点。

## 创建 CQ 并让 QP 使用它

`ibv_create_cq` 在一个 Context 下创建 CQ，QP 的初始化属性引用它。下面创建一个请求容量为 32 的忙轮询 CQ：

```c
struct ibv_cq *cq = ibv_create_cq(ctx, 32, NULL, NULL, 0);
if (!cq) return -1;
```

CQ 容量限制尚未取走的完成条目数量。一个 CQ 被多个 QP 共用时，要考虑合计完成量；发送与接收共用时，也要同时计入两个方向。容量不足可能产生 CQ overrun，这会破坏正常完成处理，不能把它当成普通业务请求的排队。

## 轮询与识别请求 {#polling}

下面是批量轮询片段。它假设应用已经维护请求表，循环退出条件与完整错误恢复由调用方处理：

```c
struct ibv_wc wc[16];
int n = ibv_poll_cq(cq, 16, wc);
if (n < 0) return -1;
for (int i = 0; i < n; ++i) {
    if (wc[i].status != IBV_WC_SUCCESS) {
        fprintf(stderr, "wr_id=%llu status=%s qp=%u vendor=%u\n",
                (unsigned long long)wc[i].wr_id,
                ibv_wc_status_str(wc[i].status),
                wc[i].qp_num, wc[i].vendor_err);
        /* 记录失败并转入错误处理，不能走成功消费逻辑。 */
        continue;
    }
    /* 用 wr_id 找到请求，并按操作类型处理成功结果。 */
}
```

返回 0 只是当前没有条目。返回正数以后，每一项还需要检查 `status`。成功时，`wr_id` 对应投递时保存的标识，可以是请求编号，也可以是寿命受到保护的上下文地址。

`wr_id` 使用指针并没有延长对象寿命。如果完成还可能到达就释放对象，下次读取这个指针仍会出错。为了便于学习，先用不同整数标识几个固定请求，再考虑动态分配上下文。

错误 WC 中只有文档规定的字段可以解释，包括 `wr_id`、`status`、`qp_num` 和 `vendor_err`。`opcode`、`byte_len` 等不能沿成功路径读取。即使成功，不同操作可用的字段也不同；不能把 SEND/WRITE 完成中的 `byte_len` 当作通用吞吐统计来源，应保留提交长度。

## 完成以后可以做什么 {#completion}

在普通主机内存、没有共享修改的前提下，操作成功完成后，可按下表继续：

| 操作与完成 | 本地应用下一步 |
|---|---|
| SEND / WRITE 发送完成 | 复用本地源缓冲区 |
| RECV 完成 | 按有效长度消费接收缓冲区，随后补充接收请求 |
| READ 完成 | 读取本地结果缓冲区 |
| Atomic 完成 | 读取返回的远端旧值，判断业务结果 |

这些规则只处理本次操作的设备访问。如果另一个请求或业务线程仍引用同一区域，就不能仅凭这一条完成归还整块内存。一个共享 CQ 暂时为空，也不能证明所有 QP 都已空闲。

远端是否消费完数据是另一个问题。WRITE 完成允许本端复用源，接收方可能还在处理目标。要重复写同一远端区域，需要接收方返回可复用的确认或额度。[2.7](07-rdma-write.md)会把这一步放进连续传输协议。

## 忙轮询与事件通知 {#events}

持续轮询可以很快发现完成，但线程在没有数据时也会占用 CPU。另一种方式是创建 completion channel，让线程在 CQ 有事件时醒来，再调用 `ibv_poll_cq`。

事件只是提醒，不携带业务完成本身，而且一次通知可以对应多个完成。正确组织时，需要防止“检查完 CQ 为空、准备睡眠期间完成已经到达”的竞态。常见做法是先通过 `ibv_req_notify_cq` 布置通知，再检查 CQ；取得事件后，为下一轮重新布置通知，然后排空 CQ，并用 `ibv_ack_cq_events` 确认已取得的事件。

有时事件到达时 CQ 已被轮询取空，这是正常竞态，不能认为设备报错。通知通常为一次性布置，需要重新请求。完整事件循环可对照 [ibv_get_cq_event 示例](https://github.com/linux-rdma/rdma-core/blob/master/libibverbs/man/ibv_get_cq_event.3)。

最小实验先用忙轮询，便于看到每条结果。优化时再比较忙轮询、阻塞等待与短时轮询后等待的策略，同时记录 CPU 使用量与尾延迟。

## 在配套实验中数一数完成

`03_rc_loopback` 让 A、B 共用一个 CQ。SEND/RECV 阶段会取到发送完成和接收完成；普通 WRITE 阶段只取发起方完成。观察 `wr_id` 与操作类型，比对两种操作为什么需要不同数量的结果。

如果所有发送都不请求成功完成，应用将缺少回收发送进度的依据。选择性生成完成需要周期性标记及尾部处理，见[批处理与流水线](../04-optimization/02-batching-pipeline.md)。初学实验保持每条请求都 signaled 更容易验证。

清理时先停止使用 CQ 的提交与处理线程，销毁关联 QP，处理事件引用，最后调用 `ibv_destroy_cq`。接下来用 [SEND/RECV](06-send-recv.md)观察双方各自得到的完成。
