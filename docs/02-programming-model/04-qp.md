# 2.4 Queue Pair

MR 让网卡知道怎样访问内存，QP（Queue Pair，队列对）则承载要执行的工作。应用把请求投递到 QP，网卡依据其中的连接、路径和权限配置执行。创建一个 QP 并不等于已经连到对端，资源创建和连接配置是两个阶段。

本章以 RC（Reliable Connected，可靠连接）为主。示例所用的 CQ 已经创建，暂时只需把它理解为存放执行结果的队列，下一章再讲取回结果的过程。

## 发送队列与接收队列

一个普通 QP 包含 SQ（Send Queue）和 RQ（Receive Queue）。SQ 发起操作，RQ 预先提供接收空间。

| 队列 | 接口 | 放入的工作 |
|---|---|---|
| SQ | `ibv_post_send` | SEND、WRITE、READ、Atomic |
| RQ | `ibv_post_recv` | 供 SEND 或 WRITE with Immediate 消耗的接收请求 |

表 2-5：发送队列与接收队列。
{: .table-caption }

函数名 `post_send` 表示向 SQ 投递，不要求请求类型一定是 SEND。READ 也通过它发起。普通 WRITE 和 READ 直接访问授权地址，不需要远端为每次操作投递 RECV。

RC QP 对应一个连接对端，提供可靠传输。UC 支持不可靠的连接传输，UD 按数据报发送，能力和消息限制不同。学习当前示例时保持 RC 不变，避免同时更换操作和传输服务类型。

## 创建 QP 与申请容量

下面的片段假设 PD 和 CQ 已准备好，请求一个小型 RC QP：

```c
struct ibv_qp_init_attr init = {
    .send_cq = cq,
    .recv_cq = cq,
    .qp_type = IBV_QPT_RC,
    .cap = {
        .max_send_wr = 16,
        .max_recv_wr = 16,
        .max_send_sge = 1,
        .max_recv_sge = 1,
    },
    .sq_sig_all = 0,
};
struct ibv_qp *qp = ibv_create_qp(pd, &init);
if (!qp) return -1;
```

队列深度限制能保留的未回收请求数，SGE 数量限制一条请求能引用多少段本地内存。创建成功后，`init.cap` 返回实际容量，应以返回结果安排请求，而不是假设申请值与硬件容量完全相同。

发送和接收可以共用 CQ，多个 QP 也可以共享它。共享以后，完成处理就需要可靠的请求标识，CQ 容量也要计入所有来源。

`sq_sig_all = 0` 时，发送 WR 通过 `IBV_SEND_SIGNALED` 单独请求成功完成。设为非零则为每条发送 WR 报告成功完成。接收完成和错误完成不由这个成功通知开关屏蔽。

## 配置 RC 连接 {#connect}

新 QP 处于 RESET。双方交换 QP 编号、初始包序列号 PSN 和路径地址后，分别配置本地 QP：

```mermaid
flowchart LR
    R[RESET] -->|本端端口和权限| I[INIT]
    I -->|对端和接收路径| T[RTR]
    T -->|发送与重试参数| S[RTS]
```

图 2-1：配置 RC 连接。
{: .figure-caption }

状态转换使用 `ibv_modify_qp`。结构体中填写字段，`attr_mask` 指明本次设置哪些字段。以下片段展示 INIT 转换，`port_num` 为本端选择的端口：

```c
struct ibv_qp_attr attr = {
    .qp_state = IBV_QPS_INIT,
    .pkey_index = 0,
    .port_num = port_num,
    .qp_access_flags = IBV_ACCESS_REMOTE_WRITE | IBV_ACCESS_REMOTE_READ,
};
int mask = IBV_QP_STATE | IBV_QP_PKEY_INDEX |
           IBV_QP_PORT | IBV_QP_ACCESS_FLAGS;
int rc = ibv_modify_qp(qp, &attr, mask);
if (rc != 0) {
    fprintf(stderr, "QP INIT: %s\n", strerror(rc));
    return -1;
}
```

这类 Verbs 接口失败时返回错误号，日志应按接口约定解释返回值，不能总是读取 `errno`。完整的 RTR、RTS 配置可对照示例的 `connect_qp`，字段来源如下：

| 转换 | 主要字段 | 信息来源 |
|---|---|---|
| INIT | `port_num`、`pkey_index`、`qp_access_flags` | 本地端口、分区和权限策略 |
| RTR | `dest_qp_num`、`rq_psn`、目标 LID/GID | 对端交换的信息 |
| RTR | `path_mtu`、`ah_attr` | 两端与网络共同支持的路径配置 |
| RTR | `max_dest_rd_atomic`、`min_rnr_timer` | 本端响应 READ/Atomic 的资源及 RNR 等待设置 |
| RTS | `sq_psn`、`max_rd_atomic` | 本地发送序列及双方协调的发起窗口 |
| RTS | `timeout`、`retry_cnt`、`rnr_retry` | 可靠传输重试策略 |

表 2-6：配置 RC 连接。
{: .table-caption }

RTR 是 Ready to Receive，RTS 是 Ready to Send。`rq_psn` 与对端的初始发送序列相配，`sq_psn` 则是本端的初始发送序列。

RoCE 的目标 GID 来自对端，本端 `sgid_index` 来自自己的 GID 表。它是本机编号，两端无需取同一个数字。`path_mtu` 也要按双方及路径能力确定，不能只取一端的最大值。

示例中的 `timeout = 14` 是编码值，按普通非零编码计算约为 67.1 ms，并非 14 ms。`rnr_retry = 7` 表示无限 RNR 重试。它们用于这个小程序，不代表服务应该无限等待；第三篇解释重试，第四篇再引入应用截止时间。

## 投递请求与处理部分失败 {#posting}

单个 WR 用 `next = NULL` 结束，也可以把多条 WR 连成链表，一次提交：

```c
struct ibv_send_wr *bad = NULL;
int rc = ibv_post_send(qp, first_wr, &bad);
if (rc != 0) {
    fprintf(stderr, "post failed: %s\n", strerror(rc));
    /* bad 及其后续未被此次投递接受；前面的请求仍需追踪。 */
}
```

假设链表是 A→B→C，B 被拒绝，A 可能已经进入队列。重新提交整个链表可能重复执行 A。应用要保留已接受部分的请求状态，分别处理其完成。

普通投递返回后，WR 和 SGE 描述本身可由应用重新构造，非 inline 数据缓冲区仍需保留。使用 `IBV_SEND_INLINE` 时，payload 在投递期间复制进工作项，成功投递后可以复用源数据；它受 QP 实际 `max_inline_data` 限制，也不表示远端已收到数据。

队列满时扩大容量可能缓解短时突发，但不能代替完成处理。若应用不断投递却不回收发送进度，最终仍会用尽资源。批量和减少完成数量的取舍见 [4.2](../04-optimization/02-batching-pipeline.md)。

## 观察创建结果与连接状态

`02_resource_lifecycle` 会打印申请与实际返回的 QP 容量，并将 QP 改到 INIT。`03_rc_loopback` 则建立一对 RC QP，使 A 和 B 在同一进程中通信：

```bash
./examples/programming_model/02_resource_lifecycle -d mlx5_0 -p 1
./examples/programming_model/03_rc_loopback -d mlx5_0 -p 1
```

RoCE 环境若需指定 GID，`03_rc_loopback` 使用 `-g` 选项。程序的 READ/Atomic 窗口请求为 4，需设备支持。这个环回实验便于观察对象关系，不能验证跨机器交换机和网络路径。

`ibv_query_qp` 可查询状态，`ibv_destroy_qp` 销毁对象。销毁前停止新的提交，并安排在途请求及资源回收；单次状态查询不能替代与其他线程的同步。接下来通过 [CQ](05-cq.md)把请求和结果关联起来。
