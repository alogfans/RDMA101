# 3.6 RoCE 网络基础

第一篇用 IP 地址建立控制连接，RDMA 请求则通过选定设备端口和 QP 路径发送。RoCE 把 RDMA 传输放到以太网上，因此要把普通网络配置与 Verbs 地址信息对应起来。

本章先找到正确地址，再讨论 MTU 和拥塞。网络管理策略依环境而定，教程中的检查命令不要求修改共享交换机配置。

## GID 与本地地址表 {#gid-config}

GID 是 128 位的全局标识。RoCE 的 GID 表条目与本地网络接口、地址和 RoCE 类型有关，`gid_index` 只是本机表中的索引。对端传来的是目标 GID，本端选的是自己的源条目。

先查看设备与网络接口关系，再查看所选端口的地址信息：

```bash
rdma link show
ibv_devinfo -d mlx5_0 -v
ip addr show
```

系统也通过 sysfs 提供条目。例如检查端口 1 的索引 3：

```bash
cat /sys/class/infiniband/mlx5_0/ports/1/gids/3
cat /sys/class/infiniband/mlx5_0/ports/1/gid_attrs/types/3
cat /sys/class/infiniband/mlx5_0/ports/1/gid_attrs/ndevs/3
```

路径和索引要替换为本机实际值。三个文件分别帮助确认地址、类型和关联接口。两台机器都用索引 3 并不说明选中了兼容路径；一端索引 1、另一端索引 3 也可能完全正确。

RoCEv2 使用 IP/UDP 封装，路径还受路由、VLAN 和网络策略影响。初次实验优先采用 perftest 正常选择的条目，再把它与自己的程序配置对照。

## MTU 要沿整条路径确认

应用消息大小与包 MTU 是两回事。64 KiB 的 WRITE 可以拆成多个包；配置更大的 path MTU 不意味着远端 MR 必须按这个大小分配。

路径可用 MTU 受两端和中间网络共同约束。查看 RDMA 端口的 `active_mtu`，也要确认底层接口及网络允许相应封装。只把某一台主机的以太网 MTU 调大，无法让不支持的交换路径自动工作。

```bash
ip link show eth0
ibv_devinfo -d mlx5_0 -i 1
```

记录当前配置以后，用匹配参数的双端测试验证。参数不合法可能在 QP 转换时失败，路径问题也可能到传输阶段才暴露，两类现象需要分别保留日志。

## 拥塞时，设备与网络怎样配合

多个发送方汇聚到同一个出口时，队列可能持续增长。以太网交换机可以通过 ECN 标记拥塞，端点根据拥塞反馈降低注入速率；DCQCN 是 RoCE 中常见的一种速率控制机制。

PFC 则按优先级暂停链路上的流量，用于控制特定队列继续接收数据。它与端到端拥塞控制承担不同作用。暂停过多可能让影响扩散，不能把“启用了 PFC”理解为延迟和可靠性问题全部解决。

RoCE 网络是否采用无损配置、哪些流量进入哪个优先级，应服从实际网络设计。应用侧不能仅修改一个环境变量就推断整个网络已使用预期策略。

## 把网络现象与应用等待联系起来

如果应用吞吐下降，先确认实际流量走的端口，再比较实验前后的计数器差值。累计丢包或暂停次数可能来自之前的负载，不能直接归因于本次请求。

```bash
ethtool -S eth0
rdma statistic show
```

可用计数器及名称依驱动和设备而异。把重传、丢弃、ECN/PFC 等可用指标，与应用的请求数、在途字节、完成速率和等待时间一起记录。

若网卡几乎没有发送、软件提交队列却很长，先查 worker 是否推进；若链路忙但小请求尾延迟上升，再考虑竞争和排队。没有网络错误也不能证明主机内存、PCIe 或应用调度没有瓶颈。

本章的练习可以保持程序不变，只记录两端实际使用的设备、端口、GID、MTU 和网络接口，说明每项来自哪里。随后在[主机拓扑](07-pcie-numa-cache.md)中补上 CPU 与内存的位置，得到完整数据路径。
