# 3.2 Verbs、Provider 与内核

打开设备、注册内存和投递请求，看起来都是 C 函数调用，实际涉及的组件却不同。前两类操作要建立受保护的设备资源，后者可以使用已经准备好的队列。这个分工解释了 RDMA 如何减少高频系统调用。

## 公共接口与设备实现

Linux 的 `libibverbs` 提供公共 API，应用因此可以用同样的函数打开不同厂商的设备。设备特有的队列格式和投递细节由用户态 Provider 实现。以 mlx5 为例，投递函数进入对应 Provider 后，才把 WR 转成设备工作项。

| 组件 | 运行位置 | 主要职责 |
|---|---|---|
| 应用与 `libibverbs` | 用户态 | 组织请求、使用公共接口 |
| mlx5 Provider | 用户态 | 编码工作项、发布门铃、解释完成 |
| uverbs / RDMA core | 内核 | 接收资源管理请求、检查并管理对象 |
| `mlx5_ib` | 内核 | 建立 mlx5 RDMA 资源和状态 |
| `mlx5_core` | 内核 | 协调更底层设备及固件功能 |

## 资源创建时为什么需要内核

普通用户程序不能自行决定哪些物理页交给设备，也不能任意映射设备寄存器。打开 Context、创建 QP/CQ、注册 MR 时，内核负责验证进程的请求并建立所需资源。

例如 MR 注册需要建立页面、DMA 映射和设备访问描述；QP 创建需要队列和设备侧上下文。用户态库通过 uverbs ABI 与内核协作，再取得句柄、返回能力和必要映射。

这部分工作往往集中在初始化、注册和连接管理中。如果应用在每次发送前重新创建资源，便会把这些成本放回高频路径。因此后面的资源复用优化需要以理解生命周期为前提。

## 使用已准备好的资源

在常规 mlx5 硬件路径上，发送队列等内存由用户态与设备共同使用。Provider 写入工作项并通知设备，轮询时读取完成队列，不必每次请求都重新向内核发起资源管理调用。

```text
资源准备：应用 → 用户态库 → uverbs / 驱动 → 设备资源
频繁投递：应用 → Provider → 队列与门铃 → 设备
完成轮询：设备 → 完成队列 → Provider → 应用
```

内核仍参与资源管理、事件与设备恢复。RXE 的实际执行路径又与硬件 Provider 不同，所以不能用软件设备的 CPU 路径证明所有 RDMA 都按同样方式旁路内核。

## 门铃映射与权限

mlx5 的 UAR（User Access Region）是允许用户进程访问的设备映射区域。Provider 对这类区域进行 MMIO 写入，通知网卡队列已经推进。写设备映射与写普通数组有不同的顺序要求，[下一章之后的队列讲解](04-qp-wqe-cqe-doorbell.md)会把二者放在一起解释。

用户态能投递并不表示可以访问任意内存。QP 的保护关系、MR key 和范围仍在设备执行时检查。减少系统调用依赖的是事先准备好的授权。

## 带着问题阅读源码

公共 API 参数先看手册和 `verbs.h`。看到投递被拒绝，再找 Provider 的请求检查；资源创建失败，则保存返回错误并结合内核日志；若设备已经产生失败 WC，回到请求上下文查实际地址和连接。

可以将示例的 `ibv_reg_mr`、`ibv_post_send`、`ibv_poll_cq` 标在一张调用图上，分别判断它们主要处于资源管理还是传输阶段。这比仅背诵“用户态/内核态”更容易对应到代码。
