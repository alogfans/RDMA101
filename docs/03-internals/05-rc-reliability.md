# 3.5 RC 可靠传输

应用只提交一条大 WRITE，网络上可能已经出现多个包。RC（Reliable Connected）负责确认这些包是否按要求到达，并在可恢复情况下重传。应用最终看到的是请求结果，而不是每个包的确认。

“可靠”有明确的作用范围：它处理已经建立的连接中的传输。进程重启、对象失效或业务重复执行，还需要应用继续管理。

## 从消息到网络包

一条 WR 描述一次操作，path MTU 则约束路径上的包大小。一块 64 KiB 数据可能被拆成许多包发送，仍对应原来的请求标识。

RC 使用 PSN（Packet Sequence Number，包序列号）追踪协议顺序。建立连接时，发送起点与对端接收期望相配。设备据此识别正常到达、缺失或重复的包，再执行相应的确认和重传规则。

因此，应用为了定位传输问题应保留 WR 标识与长度，不能把一个 WR 简单等同于一帧以太网报文。

## 没有收到期望响应时

发送方未在配置时间内得到所需响应，会按可靠传输规则重试。持续失败后，应用可能取得 `IBV_WC_RETRY_EXC_ERR`。这告诉应用重试已耗尽，但不能区分网络丢包、对端 QP 不可用和地址路径配置错误。

QP 中 `timeout` 是时间编码，`retry_cnt` 是相应重试设置；它们与应用规定的总等待时限不是同一个量。应用超时可能早于设备结束重试，设备也可能在上层等待结束后才产生完成。

把重试参数调大有时允许短暂抖动恢复，也可能让真实故障更晚暴露。应先明确允许的恢复时间，再根据负载及网络进行验证。

## RNR 是接收准备不足

当需要消耗接收请求的操作到达，而远端没有足够 RQ 资源时，会走 RNR（Receiver Not Ready）路径。发送方按 RNR 设置等待和重试。

这与一般连接重试不同。前者应先检查接收预投递和补充速度；后者需要继续检查端点与路径。普通 WRITE 和 READ 不消耗远端接收请求，WRITE with Immediate 则需要通知用的接收资源。

`rnr_retry = 7` 表示无限 RNR 重试。实验里少投一条 RECV 可能因此表现为长期等待，而非立即失败。复现实验应有外部时间限制，但终止等待后仍要理解设备引用的寿命。

## 同一连接的顺序不等于整个应用的顺序

RC 提供协议规定的传输顺序，但操作种类、fence、内存访问设置会影响可以推导的执行关系。尤其是后续操作依赖前面的 READ 或 Atomic 结果时，要按接口要求设置依赖，不能仅凭它们在同一 SQ 上排列就省掉所有同步。

多个 QP 之间没有自动建立应用需要的顺序。A 通过 QP1 写数据、通过 QP2 发“数据已到”的标志，如果没有额外协调，不能从 CPU 的提交先后推断对端一定先看到数据。

最小教程用等待 WRITE 成功完成后再通知对端，先把依赖写明确。进一步重叠执行时，再逐项证明新的顺序条件。

## 协议重传与业务重试

RC 内部重传属于原连接的传输过程。应用重新创建连接，再提交一条请求，则是新的操作。对端是否已经执行过前一次，需要通过业务身份、版本或确认机制判断。

FA 再执行一次会多加一次；WRITE 即使写入相同字节，如果目标已经归还内存池，也可能覆盖新对象。结果未知时能否重放，取决于目标在整个重试期间是否仍归本次操作所有。

可以用第一篇示例思考两种情况：client 尚未投递就断开，和 WRITE 已成功但 TCP 通知未到达。server 观察到控制连接断开时，无法仅凭同一种表面现象判断两种情况。第四篇的[故障恢复](../04-optimization/05-failure-recovery.md)会继续解决这个问题。
