# 4.4 连接管理与元数据

最小程序通过一条 TCP 连接交换 QP 信息、地址和 key。进程一直存在，内存也不变化，所以交换一次就够。服务开始处理许多对端以后，需要把这些信息保存起来，还要知道它们何时失效。

## 分开名字、实例与内存

“worker-3”可以是稳定服务名，但这个名字背后的进程可能已经重启。新进程的 QP、端口、地址与访问凭证未必与旧实例相同。

| 信息 | 用途 | 典型失效原因 |
|---|---|---|
| 服务名 | 找到要联系的角色 | 调度或配置变化 |
| 实例身份或代次 | 区分前后两次进程运行 | 重启或替换 |
| 连接信息 | 建立实际传输路径 | QP 重建、地址变化 |
| 内存地址、范围与授权 | 指定可访问对象 | 注销、释放、重新分配 |

如果应用只按服务名缓存所有信息，名字不变时就可能继续联系旧端点。将实例变化与内存变化显式纳入版本或失效机制，才能让缓存具有明确寿命。

## 控制面发布什么

集中元数据服务可以保存端点与内存描述，应用查询以后建立连接；点对点握手则由双方直接交换。两种方式都需要定义发布顺序：资源应先准备完成，再让外部看到可使用的描述。

退出时，先停止发放新授权，并撤下可发现的描述；随后协调已经取得描述的访问者，让旧引用结束，再销毁资源。仅从元数据服务删除条目，不能撤回客户端已经缓存的地址。崩溃没有正常退出流程，需要存活检查、租约或其他失效规则处理遗留信息。

元数据读取失败也有不同含义。明确返回对象不存在，与暂时连不上元数据服务，不应未经区分就推断出相同结论。接口表达能力不足时，缓存策略必须说明选择的保守行为及代价。

## 连接复用与按需建立

为每条请求重新建连开销很高，长期保留所有对端连接又可能耗尽资源。常见做法是按需创建、复用活跃连接，并回收空闲连接。

回收前要停止向连接提交新请求，等待与它关联的操作安全结束，再释放 QP 等对象。把连接从查找表中删除，只能阻止后续查找，不能让其他线程已经取得的引用自动失效。

同样，刷新元数据不应让正在执行的请求突然使用新旧混合信息。一次提交要记录实际使用的实例和内存描述，以便失败时知道访问的是哪一代对象。

## 用一次重启检验设计

先让 A 成功访问 B，保留 A 进程，再正常退出并重新启动 B。观察 A 的下一次请求是否识别变化、刷新描述、建立新连接，并重新验证目标授权。

随后可以在隔离实验中模拟 B 非正常退出。记录失败何时被上报、哪些缓存被失效、健康对端是否仍能工作。不能只看重新连接成功，还要检查旧请求是否仍引用已释放的缓冲区。

Mooncake 的 [PR #3072](https://github.com/kvcache-ai/Mooncake/pull/3072)处理远端 Segment 失效后的缓存清理，[PR #3837](https://github.com/kvcache-ai/Mooncake/pull/3837)增加元数据版本检查。它们说明“获取过一次正确地址”与“长期保持地址正确”是两项不同工作。
