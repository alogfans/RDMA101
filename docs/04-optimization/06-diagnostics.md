# 4.6 可观测性与问题诊断

经过前几章，一次传输已经可以拆成准备、排队、投递、执行和完成处理。诊断的第一步，就是确定请求在哪个阶段停止了正常进展。只收集最后一行错误，往往会丢掉最有价值的过程。

| 设备不可见 | 驱动、容器设备和用户态库 | [环境](../01-introduction/02-environment-and-first-program.md#environment) |
| 注册失败 | 地址范围、权限、分配类型与资源限制 | [MR](../02-programming-model/03-mr.md) |

这些是排查起点，不是根因判定。一种现象可以有多个原因，后续观察应该帮助排除其中一部分。

## 把应用请求和底层操作联系起来

应用日志中保存请求标识，传输层再记录 batch/task 与实际底层操作的关系。失败时应能找回操作类型、长度、内存对象版本、对端实例、设备与连接标识。

WC 日志保留 `wr_id`、`status`、`qp_num`、`vendor_err`。错误操作类型从应用上下文取得，不读取无效的错误 WC 字段。大量后续 flush 可以汇总，最早错误及其上下文要完整保留。

时间线中区分请求入队、实际投递和取得完成。否则一个排队了九秒、传输了十毫秒的请求，可能被误解成网卡耗时九秒。

## 一个接收队列停滞的例子

假设服务平时不断补充 RECV，某个业务处理分支阻塞以后，没有新的缓冲区归还。随后发送端出现 RNR，最终可能报告重试耗尽及后续 flush。

先核对最早的 RNR 与接收端 RQ 可用量，再看处理线程当时停在哪里。如果网络计数器正常、接收队列已空，继续增加网络重试次数只会推迟失败。

修正后应同时验证消息正确性、RQ 能持续补充、线程恢复后请求继续完成。仅看到某次运行不再超时，不足以确认长期负载下不会重复发生。

## 没有完成时观察谁在推进

CQ 没有结果可能因为网络停滞，也可能因为请求尚未投递。先比较软件排队数量与设备在途数量，再检查 worker 栈和锁等待。

如果 worker 等待自己负责消费的满队列，网卡可能根本没有收到请求。如果设备已有在途工作，再检查 WC、异步事件、端口与连接状态。这样的分层观察可以避免过早把所有卡顿归为网络问题。

## 设备与主机观察

基本入口如下，PID、接口和设备名需替换为实际值：

```bash
ibv_devices
ibv_devinfo -d mlx5_0 -v
rdma link show
rdma statistic show
ip addr show
ethtool -S eth0
numastat -p 12345
```

计数器在实验前后各读一次并保留字段名，用增量与请求时间线比较。累计错误可能来自历史负载；主机没有异常，也不能排除交换机或另一个端点的问题。

性能问题进一步检查 PCIe 协商速率、NUMA 位置和实际 NIC。GPU 问题先确认显存分配类型、注册路径与实际传输后端，再检查 stream 依赖。

## 留下一份能复现的记录

记录两端启动命令、软件版本、硬件与驱动、设备端口与 GID、内存类型、消息大小、并发度，以及第一次异常前后的日志。若是性能回退，应有相同条件下的对照结果。

复现步骤可以逐层缩小：完整框架、TE 小程序、Verbs 工具。某一层通过，只说明它在自身条件下通过。比较时要检查两层是否实际使用同一内存类型、路径和请求模式。

下一篇把这些方法用于 GPU 数据，先从[显存与网卡的访问路径](../05-gpu-data/01-gpudirect.md)开始。
