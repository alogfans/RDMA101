# 4.2 批处理、流水线与资源复用

一次发送、等待完成、再发送下一次，程序最容易写，也最容易让网卡在请求之间空等。优化的第一步，是让准备下一条数据与执行当前传输重叠，同时减少重复资源管理。

本章仍以主机内存 WRITE 为例。先保持每条请求都报告成功，再讨论减少完成数量；这样每个变化都能单独验证。

## 用多个槽位形成流水线

先注册一个包含多个槽位的内存池，每个槽位保存一条请求的数据和标识。空闲槽位可以填入新数据，已提交槽位保持不变，完成以后才归还。

```text
空闲 → 填充 → 已投递 → 成功完成 → 空闲
                     ↘ 失败处理 → 确认可回收
```

假设有 16 个槽位，应用最多保留 16 条在途操作。发送线程不必等待第一条完成才准备第二条，但不能覆盖任何未完成槽位。远端也需要独立的可用槽位或协议额度，否则本地流水线可能加快覆盖远端尚未消费的数据。

先测一个槽位，再逐步增加。带宽不再随槽位数增长时，继续增加通常只会提高占用或排队，不一定提供收益。

## 一次调用提交多个请求

Verbs 可用 WR 的 `next` 串起链表，一次调用提交。它减少调用和发布队列进度的部分固定成本，具体设备实现决定怎样批量处理。

TE 的 batch 是应用请求集合，内部可能再拆成更多 slice 或设备操作。Tensor 的一个逻辑块也可能映射成多个区间。这三个层次的“批量”不能直接按数量画等号。

批量投递仍可能只成功一部分。失败位置之前的请求要继续处理，之后的请求则按未接受处理，不能把整个 batch 无条件重投。

## 合并数据需要满足什么条件

两块源数据地址连续，并不自动意味着可以合成一条 WRITE。远端目标也必须按相同顺序连续，范围、授权、操作方向和完成管理要兼容。

例如源区间 `[A, A+1024)` 与 `[A+1024, A+2048)` 连续，但目标分别属于两名请求的不同槽位，就不能仅为减少请求数量而越过各自的所有权边界。

SGE 可以让一个请求从多个本地区间取数，适合避免本地拼接。它不自动提供任意多个远端目标。需要多目标时，仍要构造多个操作或使用上层传输计划。

## 复用注册与连接

在每条消息之前创建 MR 或连接，会反复支付第三篇介绍的资源准备成本。预注册内存池和复用 QP，可以把这些工作移出常用路径。

复用的前提是资源仍有效。内存池要跟踪借出区域，连接池要确认对端实例未变化。元数据缓存也要区分地址仍可用与只是名称相同，下一章之后会专门讨论。

缓存应有容量和回收策略。无限保留 MR 或 QP 会消耗固定内存及设备资源，把初始化问题变成长期占用问题。

## 何时减少成功完成数量 {#signaling}

每条 WRITE 都 signaled 时，软件能直接看到每条结果。若测量显示 CQ 处理成为瓶颈，可以在同一个满足顺序条件的发送队列上周期性设置 signaled 标记，以后续成功完成推进前面请求的回收。

这种方式必须处理三件事：为标记预留队列空间，保留未报告请求的上下文，保证最后一小批也有完成依据。若所有请求都 unsignaled，而队列已经填满，就可能无法再插入所需标记。

READ、Atomic、跨 QP 操作或特殊 ordering 设置需要重新检查顺序保证。减少 CQE 数量不能替代业务通知，也不能屏蔽错误处理。

## 运行连续 WRITE 示例

`examples/pipeline/write_pipeline.c` 把前面的槽位和批量请求写成了完整程序。分别使用 `--depth 1 --batch 1`、`--depth 7 --batch 1` 和 `--depth 7 --batch 3`，可以逐步改变在途上限与投递批大小。程序为每条 WRITE 生成完成，校验目标内容后才归还槽位；[实验指南](../labs.md#pipeline)给出了完整命令和输出解释。

## 比较收益与等待

逐项比较单请求、流水线、链表 batch、资源复用，再考虑 selective signaling。每次保留相同有效数据量，统计提交时间、完成吞吐、CPU 开销和缓冲区占用。

如果应用为凑齐大 batch 而等待，低流量请求可能变慢。限制单次 batch 的数量或等待时间，是吞吐与及时性之间的具体取舍。先按[测量方法](01-measurement.md)观察，再决定如何调节。
