# 4.5 超时与故障恢复

应用等待十秒以后放弃，不代表网卡也在第十秒停止访问内存。计时发生在软件中，设备操作有自己的执行、重试和完成过程。恢复设计首先要区分“调用方不再等待”和“底层访问已经终止”。

## 请求可能停在三个位置

尚在软件队列的请求可能还没有进入设备，此时取消相对容易；已投递请求可能正在网络中，也可能已经部分写入远端；完成已经产生而尚未被应用处理时，实际数据可能已经搬完。

```text
软件等待 → 设备在途 → 完成处理 → 向业务发布结果
```

一个超时状态不足以描述所有位置。运行时至少需要知道是否接受过请求、是否还有设备或回调引用，以及是否已经得到可靠的最终结果。

例如四段 WRITE 中两段成功、两段状态未知，不能因业务请求已超时就归还全部源和目标。未知部分仍可能访问它们，目标也不能作为一个完整对象发布。

## 将失败按可知程度处理

| 观察到的情况 | 可以据此决定什么 |
|---|---|
| 提交前验证失败 | 此次请求尚未进入执行，可修正描述 |
| 确认设备工作已经结束且请求失败 | 按该操作及资源保证回收，业务再判断是否重试 |
| 已发出但未得到可信结果 | 保留必要资源和身份，进入结果未知处理 |
| 对端实例已经替换 | 旧连接和内存描述不能继续作为新实例授权 |

“确定没发出”与“发出后回复丢失”尤其不同。后者可能已经生效。如果自动重新执行，要先证明不会造成重复效果或覆盖后来的数据。

Atomic FA 不能盲目重放；WRITE 也只有在地址仍属于同一版对象、数据保持一致、相关并发访问满足条件时，才可能安全重放。幂等性来自应用协议和所有权，不能仅由操作名推导。

## 恢复连接与保护资源同时进行

发现连接失效后，先停止新提交，记录在途请求，并启动设备支持的终止或排空流程。处理完成和 flush，确认不再存在设备访问后，再注销内存和归还对象。

软件把 QP 标为“待销毁”，并不意味着设备已经销毁它；将请求状态写成 FAILED，也不意味着 completion 以后不会再提到这条请求。内部对象和业务状态可能需要不同的回收时刻。

[PR #4092](https://github.com/kvcache-ai/Mooncake/pull/4092)中的 slice 引用问题正是一个例子：逻辑状态结束后，完成处理仍可能使用对象。因此运行时还要跟踪实际尚欠的完成及处理器引用。

## 有其他路径时

多网卡或多后端可以提供另一条路径，但切换前仍要判断旧路径上的操作是否可能继续执行。两个路径同时写同一目标时，资源寿命与版本要求不能省掉。

恢复还需要预算。限制重试次数、总等待时间和同时恢复的请求量，可以避免故障时工作量不断放大。失败链路暂时冷却、恢复后重新验证，也比立即把全部负载送回去更容易稳定运行。

端口恢复事件可能遗漏或滞后，软件通常还需查询当前状态进行校验。设备恢复、连接恢复和业务恢复应分别观察，不能只看端口变成 ACTIVE。

## 做一个有限且可解释的故障实验

先运行稳定的小规模负载，再只中断一个接收进程，保持其他对端运行。记录中断时间、第一次错误、停止新提交、请求最终结果以及资源回收时间。

实验输出要区分成功、失败和结果未知，并核对健康对端是否继续推进。重新启动接收端后，验证新实例的元数据和连接，而不是只观察日志中出现了“reconnected”。

[PR #4006](https://github.com/kvcache-ai/Mooncake/pull/4006)区分派发前连接失败与派发后不确定 WRITE，其说明也限定了覆盖路径。阅读这类修复时，应保留这些范围，避免把局部恢复机制写成整个系统的 exactly-once 保证。
