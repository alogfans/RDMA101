# 4.1 RDMA 性能测量基础

前面的程序每次传输一条消息，等待完成后退出。它证明了通信正确，却还没有回答链路能持续搬多少数据，也没有说明业务要等多久。本篇先建立测量方法，再改变程序结构。

性能优化需要一个明确的观测终点。只测 `ibv_post_send` 调用耗时，得到的是提交成本；从提交前计时到成功完成，才包含设备执行与传输等待。远端业务消费结束，则还需应用确认。

## 把初始化与稳态传输分开

一个进程第一次传输往往要经历打开设备、注册、建连、第一次访问等步骤。重复使用同一组资源后，这些成本不会每次出现。

因此，记录至少分为准备阶段和传输阶段。准备阶段分别看注册、连接等耗时；传输阶段在明确预热条件后，统计完成的有效字节和经过时间。总有效带宽可以写成：

```text
有效带宽 = 测量区间内成功完成的有效字节 / 测量区间时长
```

失败、重试产生的网络字节不能重复当成有效业务字节。也不能把“已经提交”计作“已经搬完”，否则提交队列积压时会得到虚高吞吐。

## 延迟与吞吐回答不同问题

延迟关心一次操作需要多久；吞吐关心一段时间内完成多少工作。增加并发可以填补等待空隙，提高吞吐，但也可能增加队列等待，使单请求延迟上升。

除了平均值，服务还常观察 P50、P99 等分位数。P99 表示观测样本中约 99% 不超过的延迟，需要足够样本与明确的取样方法。不同消息大小混在一个分布里时，还应按请求类别分开观察。

一个固定并发的闭环测试会在请求变慢时自然降低发起速度。若目标是验证外部请求持续到达时的排队，则还需要按到达率驱动的负载，并把排队时间纳入统计。两种测试对应不同问题。

## 估算需要多少在途数据

要让链路在等待响应期间继续工作，通常需要足够的在途数据。带宽与往返时间的乘积给出一个初步量级：

```text
在途数据量 ≈ 目标带宽 × 往返时间
```

例如用假设的 50 GB/s 和 10 μs 估算，需要约 500 KB 在途数据。若每条 64 KiB，数量级约为 8 条。这只是估算，不是实测结果或最佳队列深度；PCIe、设备窗口、软件处理和业务确认都可能改变实际需求。

这个计算有助于解释为什么逐条发送、逐条等待不能用满高速链路，也能避免一开始就把并发设到极大。

## 建立第一组对照

perftest 的选项随版本可能变化，先查看本机 `ib_write_bw --help`。以下用持续时间、消息大小和发送深度组织两端测试：

server：

```bash
ib_write_bw -d mlx5_0 -s 65536 -t 16 -D 10
```

client：

```bash
ib_write_bw -d mlx5_0 -s 65536 -t 16 -D 10 10.10.10.3
```

设备和地址替换为第一篇已经验证的配置。保持两端版本与选项一致，先固定消息大小，逐次改变深度，例如 1、4、16、64；再固定合适深度，改变消息大小。不要同时改变线程数、网卡数和 NUMA 位置。

每次保留完整命令及输出，记录单位。Gb/s 与 GB/s 相差八倍，工具使用的 MB/MiB 约定也应按输出说明确认。

| 记录项 | 为什么需要 |
|---|---|
| 版本、设备、端口、GID、链路与 MTU | 确认比较的是同一条路径 |
| 消息大小、深度、QP 数、时长 | 确认负载形态 |
| CPU/NUMA、内存类型 | 判断主机路径差异 |
| 有效带宽、完成延迟、CPU 使用量 | 同时看性能收益与成本 |
| 错误与重试、实验前后计数器 | 避免把恢复或异常混入正常结果 |

## 从工具结果走向业务结果

perftest 可以验证特定传输条件下的能力。TE benchmark 还包含请求组织与引擎运行开销，推理服务又加上队列、计算、通知和调度。因此三层结果不应互相替代。

优化前先写清假设，例如“当前请求太小，单次提交固定成本占比较高”。下一章增加 batch 后，检查提交 CPU 时间是否下降，再看尾延迟是否变差。若只看总带宽，很容易忽略一部分请求在批次中等待更久。
