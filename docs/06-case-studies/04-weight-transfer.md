# 6.4 模型权重的加载与同步

权重传输既可能发生在推理实例启动时，也可能发生在训练更新之后。前者关心实例多久可以接收请求，后者还关心正在服务的计算何时切换到新版本。

Mooncake 的[生态说明](https://github.com/kvcache-ai/Mooncake/blob/5772765c5070cd44db78629864db3c00e5239b70/README.md)列出相关集成；[checkpoint-engine](https://github.com/MoonshotAI/checkpoint-engine)提供了区分广播更新与点对点补充实例的案例。外部项目说明按 2026-09-25 查阅结果使用，实际部署应记录自己的提交与依赖版本。

## 一版权重由许多区间组成

模型权重通常不是一块简单连续内存。不同参数、分片和 dtype 可能产生大量区间。直接为每个小片段都单独分配、注册和传输，会放大初始化与请求管理成本。

可以先根据布局形成有限大小的 bucket，再组织注册和 batch。但打包有复制成本，使用原地多区间传输则有更多请求，二者需要结合模型与分配方式测量。

假设二维参数按行切成两份，目标却按列切分。目标每一份都需要从两个源分片中取相应区间。TE 能搬运列出的字节，源到目标的分片映射仍要由上层计划生成。量化格式变换或数值转换又是另一项计算，不能靠改变地址完成。

## 单接收方与多个接收方

向一个新实例补齐权重，可以选择已有数据源，按目标需求发送。许多实例同时更新时，则需要考虑源出口、接收端入口和网络共享瓶颈。

checkpoint-engine 的文档明确区分 Broadcast 与 P2P：P2P 路径使用 Mooncake TE 为动态加入的实例提供权重，广播路径有自己的更新流程。不能把整个项目中的通信都统称为 TE 逐个 WRITE。

教学上可以先使用一个源、一个目标，再增加第二个目标。比较源总发送量、各目标完成时间和其他在线请求的尾延迟，观察并发增加以后瓶颈在哪里。

## 数据到齐以后才能发布版本

将权重 v2 的区间逐步写入，不表示某一时刻就可以让任意计算同时读取 v1 和 v2。上层需要定义版本一致的消费方式。

一种容易解释的设计是把 v2 准备到独立空间，全部区间传输与必要转换完成后，再切换可见版本；旧版本要等仍在使用它的计算结束后回收。另一种原地更新方式减少额外显存，但需要协调正在执行的工作。这里描述的是设计选择，不声称所有框架采用同一种协议。

```text
准备 v2 目标 → 搬运并核对 → 建立 GPU 依赖 → 发布 v2
                                      旧 v1 仍有读者时继续保留
```

发生失败时，已经写入的部分区间不能作为完整新版本。重试还要确认目标 allocation 与版本仍属于本轮更新，避免迟到写覆盖下一轮数据。

## 区分启动成本与更新成本

启动阶段可能受大量注册和元数据处理限制；稳态更新可能更多受有效带宽、接收方数量和 GPU 拷贝影响。分别记录准备、传输、转换、等待切换及最终可服务时间。

可以用带版本和区间编号的数据模式做缩小实验：目标验证每个区间都属于 v2，再允许“发布”。中途停止一条传输，检查发布是否被阻止。这个实验检验的是上层完整性，单条 RDMA 成功并不能代替它。

新型 reshard adapter 可以将布局计划映射成 TE batch，但应按已合并与未合并状态区分。调研时 [PR #4293](https://github.com/kvcache-ai/Mooncake/pull/4293)尚未合并，适合阅读接口与所有权设计，不能当作当前安装包必然具有的功能。
