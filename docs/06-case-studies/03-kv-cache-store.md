# 6.3 分层 KV Cache 与共享缓存池

PD 分离解决一次请求在两个计算阶段之间的交接。共享 KV 缓存还希望以后遇到相同可复用前缀时，直接取回已有数据。于是系统除了搬运字节，还要识别对象、判断是否有效，并决定何时淘汰。

本章以 Mooncake 快照 `5772765c5070cd44db78629864db3c00e5239b70` 的 [vLLM 缓存集成](https://github.com/kvcache-ai/Mooncake/blob/5772765c5070cd44db78629864db3c00e5239b70/docs/source/deployment/integrations/vllm/kv-cache-storage.md)与 [SGLang HiCache 集成](https://github.com/kvcache-ai/Mooncake/blob/5772765c5070cd44db78629864db3c00e5239b70/docs/source/deployment/integrations/sglang/hicache-integration-v1.md)为例，区分框架、Store 与 TE 三层。

## 不同层保存不同职责

GPU 空间有限，可以把暂时不用的 KV 移到主机内存或远端缓存池；容量需求进一步增加时，还可能利用 SSD。越靠近计算的层通常访问路径越短，容量与成本则有不同取舍。

| 层次 | 主要决定 |
|---|---|
| 推理框架 | 哪个请求需要哪些 KV、是否与当前模型和布局兼容 |
| Store | 对象位置、存在性、分配、保留、淘汰及配置范围内的副本管理 |
| TE | 按描述将有效地址区间搬到目标 |

TE 的 WRITE 成功不等于某个缓存键已经向读者发布。Store 完成对象发布，也不必然等于数据已经持久化到磁盘。每种保证都应在负责的那一层确认。

## 沿一次缓存命中走下去

框架先根据请求和缓存规则查找可复用对象。命中以后，目标 GPU 或主机缓冲区要有容量，Store 提供可访问的位置，TE 搬运数据，接入层建立消费依赖，计算才可以继续。

“命中”省去了重新计算的机会，但新增了查找、排队、取回和可能的布局处理。如果数据很小或取回很慢，命中未必比重算更有利。

预取可以提前发起搬运，让通信与其他计算重叠。预取太多则占用显存和网络，挤压真正需要立即处理的请求。因此预取深度也受背压与容量约束。

## 写入和淘汰也会使用带宽

KV 从 GPU 回写到较低层时，需要保留源，直到对应传输安全结束。对象变为可读还要符合 Store 的发布协议，避免其他客户端读到尚未写完的内容。

淘汰不能只删除对象名就立即复用物理区域。正在读取的客户端可能仍持有地址，系统需要按自身引用或租约规则协调。第四篇的“元数据失效”在这里对应的是缓存对象寿命。

缓存键的有效性也与模型版本、布局及业务命名空间有关。只看 token 文本相同，就默认不同模型或权重版本的 KV 可共享，可能得到错误结果。

## 设计一次命中与未命中的对照

先在同一模型和配置下测首次请求，再重复有共享前缀的请求，记录命中范围、避免的计算量、实际取回字节和 TTFT。随后改变远端缓存容量或背景回写流量，观察收益是否仍然存在。

不要只比较命中率。一个较高命中率可能伴随更长的远端排队；一个较大的缓存池也可能带来注册、主机内存和管理开销。

教学实验可以先用固定大小对象模拟缓存：将已知字节写入远端池，再读取并校验，最后验证对象删除或版本更新后旧描述不再被继续使用。这个模型对应核心职责，具体淘汰算法则留给 Store 专门文档。
